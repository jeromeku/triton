# Triton’s Python-level languages — core vs standard vs semantic
https://chatgpt.com/share/68c0325b-6810-8011-a0f4-15e25059861b

This document is a practical map of the three layers that live under `triton.language` and how they feed the JIT pipeline (`@triton.jit`) down to MLIR and device code.

## What the three layers are

- **`triton.language.core` (“core”)** – the *primitive* building blocks. Think 1:1 (or very close) wrappers over Triton IR/MLIR ops: `load`, `store`, `fma`, `exp`, `program_id`, barriers, atomics, etc. These are intentionally thin and “unsafe” in the sense that they assume you already have correct shapes/strides/masks. The “core” layer is what the semantic layer ultimately lowers to before IR building.

- **`triton.language.semantic` (“semantic”)** – the Python-side *tensor semantics* and operator overloading. This layer implements broadcasting, type promotion, scalar-vs-tensor rules, and `__add__/__mul__/…` dunder operators for the Triton Tensor wrapper used inside kernels. It defines how expressions like `a + b`, `where(mask, x, y)`, and `x.reshape(...)` behave at Python time, and how they are translated into the core ops graph before emitting MLIR/TTIR.
  - Official docs describe these semantics (type promotion, broadcasting, differences from NumPy). citeturn19view0
  - The actual `semantic.py` file is the place where many of these behaviors (e.g., boolean/float/int promotion rules, method sugar, etc.) live; various issues and PRs reference concrete lines in this file, confirming the location and responsibilities. citeturn5search12turn5search6

- **`triton.language.standard` (“standard”)** – the high-level *algorithm library* written *in Triton itself* on top of the primitives. This is where you find scan/sort/histogram/top‑k patterns, composite iterators, etc. These functions are ordinary Python functions/kernels implemented with `tl.*` ops and compiled by the JIT; they are not new primitives. Release notes repeatedly add features here (bitonic sort/top‑k, masked histograms, etc.). citeturn14search0
  - Several issues/PRs reference `python/triton/language/standard.py` and specific helpers used by sort/scan, establishing this file as the home for these algorithms. citeturn5search3

Visually:

```
Python kernel code you write
  └─ uses tl.* names
     ├─ semantic: operator overloading, promotion/broadcasting, method sugar
     │     └─ rewrites/normalizes to core calls + SSA-ish exprs
     ├─ standard: library routines built with tl.* (compiled like your code)
     └─ core: thin wrappers → IR builder (TTIR) nodes
           ↓ MLIR (tt / ttg / nvgpu / … dialect passes) ↓
           LLVM IR ↓ PTX/HCN/… ↓ GPU
```

## How `@triton.jit` binds Python to the compiler

- The decorator is defined in `python/triton/runtime/jit.py` and wraps your Python function in a `JITFunction`. When you call `kernel[grid](...)`, that object specializes on argument dtypes/shapes/constexprs, captures source, parses Python AST, builds the front‑end IR, and invokes the MLIR pipeline. The Sphinx API page documents the user‑visible contract (what’s in scope inside kernels). citeturn9search1
- Multiple issues show stack traces that go through `triton/runtime/jit.py` with concrete line numbers (`JITFunction.__init__`, the call wrapper lambda, etc.), confirming where the AST/source capture and specialization live. citeturn10search1turn10search2

### Debugging knobs that expose each stage

From the main repo’s README (these are *gold* when you want to peek under the hood):  
- `MLIR_ENABLE_DUMP=1` — dump the MLIR before *every* pass. Use `MLIR_ENABLE_DUMP=KernelName` to restrict.  
- `MLIR_DUMP_PATH=<dir>` — send dumps to files.  
- `LLVM_IR_ENABLE_DUMP=1` — dump LLVM IR before each LLVM pass.  
- `TRITON_REPRODUCER_PATH=<path>` — emit a pass-reproducer (self-contained MLIR) at each key compiler stage.  
- `TRITON_INTERPRET=1` — run the Triton **interpreter** (single‑threaded Python execution) instead of launching on the GPU; you can `pdb.set_trace()` inside kernels.  
- `USE_IR_LOC={ttir,ttgir}` — rebind location info for IR–PTX mapping.  
All of these are listed explicitly in the repo README. citeturn16view0

## Putting it together: how `tl.op` is resolved

Inside a `@triton.jit`’d function:

1. You import `import triton.language as tl`.
2. Python expression building uses **semantic** helpers & dunders (e.g., `x + y` calls a semantic overload, which handles promotion/broadcasting per the semantics doc, then forms an internal expression). citeturn19view0
3. That expression ultimately lowers to **core** primitives like `core.add`, `core.load`, `core.store`, etc., which are thin wrappers that call into the frontend IR builder.
4. If you call something like `tl.sort` or `tl.associative_scan`, you’re in the **standard** library: it’s ordinary Triton code that itself compiles through steps (2) and (3). citeturn14search0
5. The JIT frontend walks the function’s AST, specializes constexprs, and emits *TTIR*; from there, MLIR passes convert *TTIR → TTGIR → LLVM IR → PTX/GCN/…*. citeturn9search13

# Hands-on: code to **peek every layer**

Each snippet below is a standalone file under `code/`.

## 0) What comes from semantic vs standard vs core

`00_peek_language_layers.py` prints where selected symbols live; you’ll see algorithmic ops (e.g., `sort`) in `standard`, arithmetic/broadcasting in `semantic`, and primitives in `core`.

## 1) Dump the pipeline (TTIR/TTGIR/LLIR) from a tiny kernel

`01_dump_pipeline.py` toggles the env vars from the README and compiles a toy kernel; artifacts land in a temp folder so you can open them in an editor. citeturn16view0

## 2) Show the Python AST Triton parses

`02_ast_peek.py` uses `inspect.getsource` + `ast.dump` to display the exact AST nodes the frontend consumes (handy to debug tricky Python constructs).

## 3) Run in the interpreter

`03_interpret_vs_gpu.py` sets `TRITON_INTERPRET=1` and runs the *same* kernel; add `breakpoint()` to single‑step the math instead of launching on GPU. citeturn16view0

## 4) Monkey‑patch **core** to log primitive calls

`04_monkeypatch_core_logging.py` wraps a few `triton.language.core` primitives (e.g., `load`, `store`, `where`) so you can see which core ops actually get invoked by your higher‑level semantic code.

## 5) Capture a **reproducer** for a failing pass

`05_capture_reproducer.py` sets `TRITON_REPRODUCER_PATH` so you get a self-contained `.mlir` file at every stage; if a pass crashes, you have a minimal repro to iterate with `mlir-opt`. citeturn16view0
